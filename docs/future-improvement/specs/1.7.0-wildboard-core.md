# 1.7.0 — Wildboard Core

**Label:** `future-improvement`
**Status:** Specified
**Primary outcome:** a second workspace kind — an unstructured, local-first canvas for brainstorming, ideas, and random writing

> **Status note.** `SPECIFIED`. Governed by `docs/decisions/ADR-003-wildboard-workspace-kind-and-vault.md` (**Accepted**). Implementation sprints live in `docs/future-improvement/sprints/v1.7.0/` (`WB-01`…`WB-05`). The version stays outside the active V1 board until the owner promotes it.

## 1. Purpose

Document IDE's canvas is document-centric: every object is a tracked file, and every file inherits document semantics (Word, Git, batch mutation, PDF export). That is correct for authoritative documents and wrong for a **second brain**, where the user wants to dump ideas, sketches of thought, and loose text without deciding what they are.

`1.7.0` introduces a second workspace kind — **Wildboard** — that reuses the existing canvas interaction engine but has its own object model, its own storage vault, and none of the document-only subsystems.

Product reference: Spatial (get-spatial.com). `1.7.0` covers the core of that product: sticky notes, sheets, stacks, and instant capture. Rich writing (`1.8.0`) and media/webclips (`1.9.0`) follow.

## 2. Scope

**In scope**

- `workspaces.kind` (`documents` | `wildboard`), migration, and kind-based subsystem gating.
- A per-workspace content vault with atomic file writes, recovery snapshots, and a trash.
- `space_objects` placement model and `stack_members` flat grouping.
- Object kinds `text`, `sheet`, `stack`.
- Wildboard canvas surface reusing pan/zoom/select/drag/persist.
- Quick Capture (global hotkey) creating a `text` object.
- "Open vault folder" and "Export vault" (zip) actions, so app-managed content is discoverable and backupable.

**Out of scope (later versions)**

- rich/block editing and Medium-style formatting (`1.8.0`),
- labels, layer view, wildboard search (`1.8.0`),
- images, video, links, webclips, PDF viewer, importers (`1.9.0`),
- cloud sync/backup,
- mobile applications,
- X/Twitter import.

## 3. Workspace kind & isolation

```sql
ALTER TABLE workspaces ADD COLUMN kind TEXT NOT NULL DEFAULT 'documents';
```

- `documents` — unchanged behaviour; all existing workspaces backfill to this value.
- `wildboard` — document-only surfaces are **rejected by the backend and not mounted by the shell**:
  - Microsoft Word / DOCX integration and editing-lock detection,
  - batch operation engine and batch UI,
  - PDF export,
  - sharing,
  - folder sources and reconciliation,
  - Source Control (Git) panes and actions.

Enforcement:

- **Backend.** Every workspace-scoped document route returns `409 { "errorCode": "WorkspaceKindNotSupported" }` for a `wildboard` workspace. Document-id routes need no guard because wildboard objects are never `documents` rows.
- **Frontend.** `GET /api/workspaces/{id}` returns the kind and a capability set; panels and tool toggles whose capability is `false` are not mounted.

Hiding or disabling a button without the backend rejection is not sufficient.

## 4. Vault layout

```text
<vault-root>/
  notes/
    <object-id>.md        # text and sheet objects
  links/
    <object-id>.md        # reserved for 1.9.0
  assets/                 # reserved for 1.9.0
```

- The vault root is `%LOCALAPPDATA%\DocumentIDE\vaults\<workspaceId>\`, created on first write.
- Relocating the vault to a user folder is **deferred** beyond `1.7.0`; this version provides an "Open vault folder" action instead.
- Every file is written with the same discipline: write to a temp file in the same directory, validate, then move (new file) or replace (existing file) onto the target.
- A `text` object's file contains the note body as plain Markdown. `sheet` uses the same representation.
- Object identity is the application `id`, not the filename. Renaming a title does not need to rename a file.

## 5. Domain model

```text
space_objects
- id                    UUID, primary key
- workspace_id          FK -> workspaces(id) ON DELETE CASCADE
- kind                  text | sheet | image | video | link | webclip | stack | label
- canvas_x, canvas_y    REAL
- width, height         REAL
- vault_relative_path   TEXT NULL   (NULL only for stack/label)
- mime_type             TEXT NULL
- title                 TEXT NULL
- availability_status   available | missing   (default available)
- created_at, updated_at

stack_members
- stack_id              FK -> space_objects(id) ON DELETE CASCADE
- object_id             FK -> space_objects(id) ON DELETE CASCADE
- PRIMARY KEY (stack_id, object_id)
- UNIQUE INDEX on (object_id)     -- an object belongs to at most one stack
```

`kind` lists the future kinds (`image`, `video`, `link`, `webclip`, `label`) in the schema for forward
compatibility, but `1.7.0` **rejects creating them** — only `text`, `sheet` and `stack` are creatable
and that rejection is a test (`Unsupported_Kind_For_17_Is_Rejected`).

Invariants:

- `vault_relative_path` is a normalized relative path inside the vault; absolute paths and `..` segments are rejected.
- An object belongs to exactly one workspace.
- A `stack` has no backing file.
- Deleting a stack removes only the grouping; member objects remain.
- Deleting a file-backed object requires explicit confirmation and deletes the backing file only as part of that confirmed action.
- An object belongs to at most one stack; a stack cannot be a member of a stack; stack members must share the stack's workspace.

## 6. Object kinds in 1.7.0

### 6.1 `text` (sticky)

- Rendered as a resizable card on the canvas.
- Body stored in `notes/<id>.md`.
- Inline editing of short text; long text may open a larger editor.
- Title defaults to the first non-empty line, truncated for display; the stored title is metadata only.

### 6.2 `sheet`

- Rendered as a larger paper card.
- Uses the same `.md` storage.
- Opens the Markdown editing surface (`MD-01` until `1.8.0` replaces it with the block editor).
- A sheet is a real file; it may later be promoted to a tracked document.

### 6.3 `stack`

- Flat grouping (no nesting).
- Collapsed renders as a compact pile showing a count; expanded renders members.
- Drag into and out of a stack.
- Position of the stack is independent of member positions; expanding restores relative member layout from stored coordinates.

## 7. Canvas surface

Reuse of existing components is required, not optional:

| Concern | Reused from |
|---|---|
| viewport pan/zoom/transform | `features/canvas/DocumentCanvas.tsx` |
| selection (click, additive, rect) | `features/canvas/selection/SelectionController.ts` |
| group drag | `SelectionController.groupDrag` |
| position persistence | pattern from `usePersistedPosition.ts` |
| store contract | `useSyncExternalStore` + cached snapshot |
| spatial index / tidy | `layout/SpatialIndex.ts`, `layout/TidyLayout.ts` |

Differences:

- the object source is `space_objects`, not `workspace_documents`;
- renderers are kind-specific (`text`, `sheet`, `stack`);
- double-click opens the wildboard editor, never Microsoft Word;
- the empty state offers "capture a thought" and "create sheet".

## 8. Quick Capture

- A global shortcut opens a minimal one-field panel.
- Submit creates a `text` object in the current wildboard (or a configured default wildboard) and places it at a non-overlapping position.
- `Escape` closes without writing.
- The panel performs no network I/O.
- Hotkey ownership: the desktop host (`FND-07`) registers it; the shell provides the fallback in-app binding.

## 9. File safety

- All vault paths are canonicalized under the vault root; traversal and reparse-point escape are rejected with a typed error.
- **Every replace takes a recovery snapshot of the previous content before the temp write. If the
  snapshot cannot be created, the write is blocked** (the same non-negotiable the document mutation
  engine follows: vault content is user source, not derived data).
- Writes are atomic (temp → validate → rename); a failed write leaves the previous content intact.
- Deletion is not an unlink: the backing file moves to `<vault>/.trash/` and stays recoverable until
  the user purges it. A placement-only removal never touches the file.
- No command line is constructed from titles, paths, or object metadata.
- Wildboard objects are excluded from the privileged local API and ShareHost surfaces.
- No document mutation engine is reachable from a wildboard workspace.

## 10. Persistence & lifecycle

- Placement and metadata live in SQLite.
- Content lives in the vault as plain files.
- Crash recovery: on startup, orphaned temp files are removed and objects whose backing file is missing are marked `missing` (placement retained, never silently deleted).
- Deleted files live in `<vault>/.trash/`; the trash is listed, restorable, and purgeable by explicit user action.
- Missing-file objects can be recreated empty, relinked, or removed by explicit user action.

## 11. Search & indexing

Not in `1.7.0`. Wildboard files are not inserted into `documents`, so they are not indexed by the existing FTS5 pipeline. Search arrives in `1.8.0` with a wildboard-scoped index or an explicit promotion path.

## 14. Acceptance criteria

- [ ] Existing workspaces open unchanged after migration; `kind = 'documents'`.
- [ ] A wildboard workspace exposes no Word, batch, PDF-export, or Git surface.
- [ ] Creating a sticky or sheet writes a real `.md` file in the vault.
- [ ] Editing a sticky persists to that file; reopening restores content.
- [ ] A failed write leaves the previous file content intact.
- [ ] A replace whose recovery snapshot cannot be created is **blocked**, and the existing file is unchanged.
- [ ] Deleting a file-backed object moves the file to the vault trash; it can be restored, and purge is explicit.
- [ ] "Export vault" produces a zip containing every object file; "open vault folder" opens the vault root.
- [ ] Only `text`, `sheet` and `stack` can be created in `1.7.0`; the future kinds are rejected by test.
- [ ] One object cannot be a member of two stacks (enforced by a unique index, proven by a test).
- [ ] Stacks group and ungroup without touching member files.
- [ ] Quick Capture creates a `text` object with no network I/O.
- [ ] Path-traversal and reparse-point escape attempts are rejected.
- [ ] Canvas remains responsive at 1,000 objects.
- [ ] No wildboard content appears in ShareHost or the privileged API.

## 15. Non-goals

- cloud sync or a sync backend,
- real-time multiplayer,
- DOCX creation or editing from the wildboard,
- a proprietary content format,
- creating physical folders from stacks,
- automatic promotion of wildboard files into tracked documents.

## 16. Risks & open questions

1. **Two object stores.** Search, sharing, and export must bridge explicitly rather than grow accidental coupling.
2. **UI leakage.** Gating must be verified by tests, not visual inspection.
3. **Vault discoverability — resolved for `1.7.0`.** "Open vault folder" and "Export vault" (zip) ship in this version; relocation to a user-chosen folder stays deferred.
9. **Recovery on vault mutation.** Vault content follows the document mutation non-negotiable (snapshot → temp → validate → atomic replace; a failed snapshot blocks the write), and deletes go to a restorable trash. `WB-02` owns the implementation and its tests.
4. **Size growth.** Media (1.9.0) requires quotas; plan the interface now.
5. **Resolved:** the vault lives in app data for `1.7.0`; relocation is deferred.
6. **Resolved:** sheets are wildboard-only in `1.7.0`; `documents` workspaces are unchanged.
7. **Resolved:** the in-app Quick Capture shortcut is `Ctrl+Shift+Space` (`Alt+Space` is the Windows system-menu shortcut).
8. **Deferred:** relinking a `missing` object to a different existing vault file; `1.7.0` offers "recreate empty" and "remove" only.
