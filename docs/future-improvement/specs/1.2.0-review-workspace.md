# 1.2.0 — Review Workspace

**Label:** `future-improvement`
**Status:** Specified
**Primary outcome:** structured review of document changes before final approval/commit

## 1. Purpose

Turn the existing diff and inspection capabilities into a first-class review workflow for multiple documents. Review is an inspection state, not a mutation engine.

## 2. Review session

```text
ReviewSession
- id
- workspace_id
- name
- created_at
- updated_at
- status
- baseline_strategy
- document_ids
- current_index
```

Review status:

```text
open
paused
completed
archived
```

Per-document review state:

```text
unreviewed
approved
needs_changes
skipped
```

## 3. Baseline strategy

For Git-managed documents, a review may compare the working tree against the selected Git baseline.

For non-Git documents, starting a review may create a temporary Document IDE recovery snapshot as the baseline.

The baseline is immutable during the active review unless the user explicitly restarts or resets the review.

## 4. Review workspace UX

```text
REVIEW

8 documents
3 approved
2 needs changes
3 pending

[Previous] [Next]

Selected document
    ↓
Document-aware diff
    ↓
Review state
```

The user must be able to move through the review queue without losing the current document context.

## 5. Diff integration

Markdown uses textual diff. DOCX uses the Document IDE document-aware diff. Binary Git semantics remain file-level.

The review surface must show enough context to answer:

- which file changed,
- what changed,
- whether the change was inspected,
- what action remains.

## 6. Approval semantics

`Approve` means “reviewed and accepted for this review session.” It does NOT mean:

- save file,
- stage file,
- commit file,
- push file.

A later explicit action may stage or commit approved files, subject to normal SCM semantics.

## 7. Review summary

The session summary must list:

- total files,
- approved,
- needs changes,
- skipped,
- unread/unavailable,
- baseline used.

## 8. Safety

Review never suppresses:

- lock detection,
- stale detection,
- history/recovery checks,
- Git conflict state.

## 9. Non-goals

- multiplayer review,
- comment threads in 1.2.0,
- automatic merge,
- auto-commit on approval.
