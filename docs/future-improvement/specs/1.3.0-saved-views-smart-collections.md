# 1.3.0 — Saved Views & Smart Collections

**Label:** `future-improvement`
**Status:** Specified
**Primary outcome:** reusable lenses and dynamic document sets without physical file moves

## 1. Purpose

Allow users to preserve useful searches/filters and create dynamic collections that act like virtual folders.

## 2. Saved View

A Saved View records presentation/query context such as:

```text
SavedView
- id
- workspace_id
- name
- query_expression
- sort_expression
- filter_state
- active_surface
- selected_document_ids
- created_at
- updated_at
```

A Saved View is a **lens**, not a snapshot of file contents.

Opening a Saved View re-evaluates its query against current workspace data.

## 3. Smart Collection

A Smart Collection is a virtual collection whose membership is derived from a predicate.

Example:

```text
Production Docs
folder:production type:docx
```

or:

```text
Changed This Week
modified:this-week
```

Membership is computed, not manually stored as an authoritative list.

## 4. Canvas behavior

Smart Collections may appear as canvas objects. Their placement is workspace state. Opening a collection presents its resolved members through the normal picker/list/canvas release flow.

A Smart Collection MUST NOT move files or create folders.

## 5. Query language

Reuse the existing structured query parser where possible. The feature must not create a second incompatible query syntax.

## 6. Changes and staleness

Because membership is live, the UI should show when a collection's result set changed since last open. A saved view is never considered stale solely because its results changed; it is expected to re-evaluate.

## 7. Rename/delete

Renaming or deleting the virtual object does not rename/delete files. Physical file operations remain explicit filesystem actions.

## 8. Non-goals

- database-like arbitrary formulas,
- cloud shared smart collections,
- physical folder synchronization,
- collection-level Git commits.
