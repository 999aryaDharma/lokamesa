# 1.4.0 — Document Health / Linter

**Label:** `future-improvement`
**Status:** Specified
**Primary outcome:** deterministic document-integrity and consistency checks with safe repair routing

## 1. Purpose

Continuously identify issues that affect trustworthiness, usability, or consistency of local documents.

## 2. Health model

```text
HealthReport
- document_id
- generated_at
- policy_version
- findings[]
```

Finding:

```text
FindingId
Severity
Category
Message
Location
Evidence
RepairCapability
```

Severity:

```text
info
warning
error
```

## 3. Integrity checks

Initial checks include:

### Filesystem / indexing
- missing source/file,
- permission failure,
- unreadable document,
- stale/error index state.

### Markdown
- broken local links,
- broken wikilinks,
- unresolved references,
- duplicate/conflicting structural metadata where detectable.

### DOCX
- unreadable structure,
- suspicious malformed package state,
- missing metadata expected by the configured policy,
- inconsistent heading hierarchy where detectable.

## 4. Consistency policy

Formatting findings that depend on project preference must use an explicit workspace Health Policy. Do not hard-code a single “correct” font, margin, paper size, or heading style.

Example:

```text
HealthPolicy
- expected_paper_size
- expected_margins
- expected_font_family
- expected_font_size
- heading_rules
- link_rules
```

No policy means “check integrity, do not guess style intent.”

## 5. Health UI

Document detail may show:

```text
Health
✓ 18 checks passed
⚠ 2 warnings
✕ 1 error
```

Workspace health aggregates counts and allows navigation to affected documents.

## 6. Repair semantics

A finding may expose:

```text
Review
Preview Fix
Fix
```

Any actual mutation must route through the existing batch/document mutation and recovery layers. Linter code MUST NOT mutate the file directly.

## 7. Non-goals

- subjective AI writing quality scores,
- autonomous rewriting,
- universal formatting normalization,
- replacing QA/release gates.
