**Date:** 2026-10-19
**Scope:** every shipped subsystem (frontend app shell, privileged API controllers, Desktop/WebView host,
ShareHost, installer) reviewed against `docs/specs/00-master-product-technical-spec.md` and the
`docs/quality/v1-readiness-report.md` GO claims.
**Method:** static reading + grep across `src/` with per-finding `file:line` evidence, plus targeted
test execution. Six independent read-only audits were run in parallel and the highest-severity claims
were re-verified directly.

## Verdict

`v1.0.0` ships a shell whose core data pipeline is not wired. The v1 readiness report's **GO / 19-of-19 /
22-of-22 PASS** is contradicted by code for at least the graph, share-token, share-lifecycle, search and
Quick Look gates. Two post-release hotfixes fixed three real defects (WebView2 profile, relative API
fetches, default-workspace seed) but the pipeline defects below remain.

## BLOCKER

### B1 — The indexing/search pipeline is dead at runtime
- Attaching a folder only inserts a `folder_sources` row: `FolderSourcesController` → `FolderSourceService.cs:69`.
  Nothing calls `IStartupReconciler` from the attach path.
- Even an explicit `POST /api/workspaces/{id}/reconcile` does not index: `StartupReconciler.cs:212,238`
  set `IndexStatus = "pending"` and never call `IFtsIndex` (`search_content` stays empty).
- No watcher/indexer runs in the shipped host: `FileChangeCoordinator` is never registered, no
  `AddHostedService` exists (`WebAppHost.cs:66-89`), and `IncrementalIndexCoordinator.ReindexWorkspaceAsync`
  (`IncrementalIndexCoordinator.cs:261`) has **no production caller** (only `tests/`).
- The shipped frontend never calls `/reconcile` (grep of `src/DocumentIDE.Web/src` returns only a
  comment at `workspaceApi.ts:61`); `App.tsx:576` reacts to attach by re-`GET`ting documents.
- **Consequence:** on a fresh install a user attaches a folder and sees an empty folder card, an empty
  list and empty search. The local-first document loop does not work.

### B2 — Public ShareHost does not authenticate tokens at all
- `DocumentIDE.ShareHost/Program.cs:34` runs the token middleware only when the `X-Share-Token` header is
  **present**; `ShareTokenMiddleware.cs:41-46` explicitly "proceed[s] without validation" when it is absent,
  and the file self-describes as a *"Minimal middleware placeholder … Real security logic can be added later"*.
- `ShareTokenService.GenerateTokenForShare` (`ShareTokenService.cs:143`) has **no production caller**, so the
  in-memory hash map is always empty; a request that *does* send a token is rejected (403) while one that
  omits it succeeds (200).
- **Consequence:** anyone holding a `shareId` (not a secret) can read the manifest, previews, search, graph and
  permitted downloads. This contradicts the "Public sharing" non-negotiable and the readiness §69 evidence.

### B3 — Stop/revoke never reaches the viewer
- `ShareLifecycleService.cs:123-144` only changes DB columns (`ExpiresAt`, `TokenHash`); ShareHost serves purely
  from `manifest.json`, which stores no token hash or expiry. A revoked/stopped link keeps serving indefinitely.
- The readiness wording "until its token expires" (`v1-readiness-report.md:135`) is false: there is no expiry check.

### B4 — Graph edges are never produced
- No production code writes the `relations` table. `MarkdownLinkIndexer.GetExplicitRelationCandidates`
  (`MarkdownLinkIndexer.cs:110`) and `IRelationRepository.ReplaceDerivedRelationsAsync`
  (`RelationRepository.cs:218`) have no production callers; `SemanticRelationService`, `ManualRelationService`
  and `BacklinkService` are not registered in any host. `GraphController.cs:41` therefore returns `edges: []`.
- The host test masks this by inserting relations directly (`AppShellSurfaceHostTests.cs:62-81`).
- **Consequence:** the graph view always shows nodes with no edges; adding `[[wikilinks]]`/links never creates
  an edge. Readiness §89 PASS is not supported.

### B5 — The public share path is non-functional end-to-end
- No code launches the `ShareHost` process; `NgrokTransport` is never registered; `ShareController.cs:141`
  hardcodes `tunnelError = null`; `BuildUrl` returns a relative `/share/{id}[?token=]` that 404s, because
  ShareHost exposes no `/share/{id}` HTML viewer route.
- **Consequence:** "Copy link" yields an unusable path; readiness §90/§97 PASS is not supported.

## MINOR

- `errorCode` from controllers (`MarkdownDocumentController.cs:40,60,76`, `ShareController.cs:34,120,123`)
  is not read by clients, which look for `error`/`detail` (`markdownApi.ts:34-41`, `shareApi.ts:51-59`) —
  typed refusals (e.g. `RecoveryUnavailable`, `DocxPreviewUnavailable`) never reach the user.
- Markdown "Preview" renders raw source in a `<pre>` (`MarkdownEditor.tsx:197-207`); the registered
  `MarkdownPreviewService` serves only ShareHost snapshots. Readiness §49 overstates this.
- Saving Markdown does not re-index or re-extract relations (`MarkdownDocumentController.cs:50-99`).
- Dirty Markdown edits are discarded on Close with no confirmation (`MarkdownEditor.tsx:173-177`).
- `DocxInspector`/`RelationsInspector` are unmounted (`Inspector.tsx:15-21`) — readiness §85 "Inspect reachable" overstated.
- Workspace document membership uses an unbounded `LIKE canonical_path || '%'` join (siblings leak) — `DocumentRepository.cs:132`.
- Folder-source file counts hardcoded to 0 (`AddFolderSource.tsx:55`).
- Worktree "active" state is dead (`WorktreesScreen.tsx:372-384`; `WorktreeList.tsx:26,111`).
- Default-workspace seed keys on "table empty", not "default missing" (`WorkspaceBootstrap.cs:29-33`); the dev
  API host no longer seeds (from `083ee71`) so attach-folder 500 can recur in dev.
- Installer uses `perMachine` scope with an `HKCU` key path (`DocumentIDE.wxs:6,26-32`).
- Share create is not atomic (artifacts published before the DB row) — `ShareLifecycleService.cs:91-115`.
- Download-permission gate can be bypassed with dot-segments (`Program.cs:132-148` vs `ShareTokenService.cs:106`).
- SCM service registration exists in two places that can drift (`Program.cs` vs `SourceControlServiceRegistration`).
- SCM read routes accept a caller-named repository path (documented residual; `SourceControlController.cs:400,423,…`).

## Documentation / verification-integrity issues

- `docs/quality/v1-readiness-report.md` reports GO while B1–B5 are open; several PASS rows cite behaviour the
  code does not have (graph §89, share token §69, share lifecycle §90, Quick Look §85, search §47/§87).
- `ShareTokenTests.cs` is a 0-byte file cited as token-security evidence.
- The BLOCKED → GO flip happened without closing the underlying gaps; surfaces were mounted over engines that
  were never wired, so the release gate can stay green while the product is broken.

## What is genuinely correct

Source control (complete route coverage, discard/restore fail-closed with fingerprint-bound token,
`--ff-only` pull, no force push); the Markdown safe-write pipeline (snapshot → temp → validate → atomic
replace, fail-closed when recovery is unavailable); Word COM concurrency = 1; PDF engines + mounted UI;
`PrivilegedRequestGuard` on the owner API (Origin + session token); 30-day recovery snapshots.

## Fix order (approved)

1. **B1** — wire reconcile → index and the attach flow (TDD).
2. **B2/B3** — ShareHost token authentication + cross-process enforcement of stop/revoke (TDD).
3. **B4** — populate the relation store so graph edges are real (TDD).
4. **B5** — make the public share path reachable end-to-end (TDD).
